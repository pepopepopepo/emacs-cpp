## 3. The match tiers: what the code is, and how to make it general

Upstream's owner asked, through the reviewer, "how to rewrite this code to be general and
not a 500 line regexp". What is there, on c031e2b:

- M-1. **Size and shape.** The matcher is `lisp/init-completion.el:41-116` (76 lines:
  `emacs-cpp--match-class`, `emacs-cpp--match-word-start`, `emacs-cpp--match-compile`,
  `emacs-cpp-match-tier`, `emacs-cpp-match-sort-by-tier`), its two callers
  `emacs-cpp-completion-sort` (`:119-137`, vertico's sort override) and `emacs-cpp-go--sort`
  (`lisp/init-go-to-anything.el:40-55`, `M-o`), and 19 table rows of specification in
  `test/init-completion-test.el:24-41`. Not 500 lines; about 110 with the callers. It is
  hard to read for one reason: the definition of "word start" (the string's start, after a
  non-alphanumeric, a capital after a small letter or digit, the last capital of a run
  before a small letter: `HTTPServer`'s S) is spelled three times in regexp syntax, once per
  tier, with case handled by `[xX]` classes and the run-of- capitals rule by look-ahead on
  the next input character. The regexps exist because the first version walked characters in
  interpreted Lisp at 0.5 ms per candidate (D-120, `HANDOFF.md:219-222`), and `lisp/` is not
  byte-compiled (`HANDOFF.md:34-35`; R1 `lisp_compiled: 0`).
- M-2. **What it computes.** Filtering is orderless's (`init-completion.el:177-194`:
  literal, regexp, initialism, flex; LSP 3.18's "letters in order"). Ranking is a stable
  sort of the filtered list by a tier in 1..3 per input word, the worst word deciding: 1 the
  word runs unbroken from a word start; 2 it runs unbroken anywhere, or its letters each
  start a word; 3 anything else that passed the filter. Symbols from clangd keep the
  server's order (patch 0013 ranks the same three tiers server-side). That is the whole
  contract, and it is a good one: it is clangd's, so a file list and a symbol list rank
  alike.
- M-3. **Why it is not general.** Two things: (a) the word-start predicate is not a
  function, so the rule cannot be changed, tested or reused in one place (a change for `::`,
  digits or `_` means three regexps); (b) the tier is a by-product of three regexp searches
  rather than the output of a match function that could also give the match positions (for
  highlighting; `emacs-cpp-go--highlight-first`, `init-go-to-anything.el:23`, today
  recomputes them through orderless) or a finer score (clangd's 0013 ranks inside tier 2 by
  the share of the name covered; the Lisp cannot).

Three ways to rewrite it. None is chosen here (the fork's rule: options with costs, the
owner's call); round 3 measures the two that need numbers.

- **A. Emacs 31's own `flex` scoring**
  - What changes: drop `orderless-flex` and the tier sort; let the `flex` style filter and
    rank: Emacs 31 scores each match in C with an affine-gap alignment
    (`completion--flex-cost-gotoh`, `src/minibuf.c:2334`; `minibuffer.el:4950`
    `completion--flex-cost`, sorted by `completion--flex-adjust-metadata` at `:4962`)
  - Fidelity to the 19-row spec: partial: contiguous before scattered holds (the cost is
    gap-based, `src/minibuf.c:2283-2333`: a gap costs the same wherever it opens); a word
    start is nothing special to it, so tier 1 and the substring half of tier 2 tie (`vec`
    and `ector` in `Vector.cc`, rows 1 and 5 of the spec), and initials are told from gapped
    letters by gap length only; 7 of the 19 rows would hold by construction, the rest
    UNVERIFIED until round 3 runs the table (measured 2026-10-20, M-5 in section 4b: 6 of 8
    cross-tier pairs agree, the initials rows disagree)
  - Lines: -110
  - Speed: C; the fastest possible
  - Dependencies: none new
- **B. a scoring library**
  - What changes: hotfuzz (C module plus Lisp fallback, word-boundary aware, Sublime-style),
    fussy (a completion style over flx, fzf-native or hotfuzz, sets the sort), or flx (Lisp,
    boundary heat map)
  - Fidelity to the 19-row spec: the rank is a continuous score, not three tiers; word
    starts are rewarded, so the spec's rows mostly hold, some by accident (UNVERIFIED, round
    3 runs the table)
  - Lines: -110, +20 glue
  - Speed: hotfuzz's C module: as fast as A; flx in Lisp: slower than today's regexps unless
    compiled
  - Dependencies: a new pinned submodule (D-006), for hotfuzz a build step for the module
    (`make packages`)
- **C. the same contract, as a function, compiled**
  - What changes: `emacs-cpp-word-start-p (string i)` (6 lines), `emacs-cpp-match (input
    candidate)` returning `(tier . positions)` in one left-to-right pass: tier 1 and 2's
    substring part by `string-search` (C) from each word start, initials and the subsequence
    by a short loop; `make packages` byte- and native-compiles `lisp/` as it does `lib/`
  - Fidelity to the 19-row spec: exact: the 19 rows are the function's tests; adds positions
    and the room for a finer score
  - Lines: about 45 for the matcher, -76

  is what made the code unreadable; compile the Lisp and the straightforward function comes
  back, with the spec table as its tests and the word-start rule in one place. Option A is
  the cheapest if its ranking is close enough to clangd's tiers for file names, which round
  3 decides with the table; it would also make the configuration lean on Emacs instead of on
  its own matcher, which is DESIGN's principle 2. Option B buys a better ranking than tiers
  at the price of a new dependency and a module build, and it would rank files by a rule
  clangd does not share. The sketch of C, for the owner to judge the size (not tested; a
  `fix/` branch follows round 3's numbers):

```elisp
(defun emacs-cpp-word-start-p (string i)
  "Non-nil if index I of STRING starts a word, as clangd's FuzzyMatcher segments it."
  (or (= i 0)
      (let ((prev (aref string (1- i))) (this (aref string i)))
        (or (not (or (<= ?a (downcase prev) ?z) (<= ?0 prev ?9)))
            (and (<= ?A this ?Z)
                 (or (<= ?a prev ?z) (<= ?0 prev ?9)
                     (and (<= ?A prev ?Z) (< (1+ i) (length string))
                          (<= ?a (aref string (1+ i)) ?z))))))))

(defun emacs-cpp-match-word (word candidate)
  "Return WORD's tier in CANDIDATE, 1 to 3, or nil if its letters are not in order."
  (let ((case-fold-search t) (from 0) hit)
    ;; Tier 1 or 2 by substring: `string-search' runs in C.
    (while (and (setq hit (string-search word candidate from))
                (not (emacs-cpp-word-start-p candidate hit)))
      (setq from (1+ hit)))
    (cond (hit 1)
          ((string-search word candidate) 2)
          ((emacs-cpp-initials-p word candidate) 2)
          ((emacs-cpp-subsequence-p word candidate) 3))))
```

  `emacs-cpp-initials-p` and `emacs-cpp-subsequence-p` are two 8-line loops;
  `emacs-cpp-match-tier` keeps its signature (the maximum over the input's words, nil
  becoming 3 as today since orderless filtered first) so the two callers and the 19 rows do
  not change. `string-search` is case-sensitive, so the candidate and the word are downcased
  once each (the regexps' `[xX]` classes did the same work per character).
